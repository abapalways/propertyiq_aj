# PropertyIQ

A property-matching search agent built for the PropertyIQ Challenge (Team Beyond AI Engineering course).

PropertyIQ combines exact metadata filtering, hybrid semantic + keyword search, and an NLI-based
contradiction check to return real-estate listings that genuinely match a buyer's stated criteria —
not just listings that _look_ similar to the query. It runs as a chat agent in a Gradio UI, with
tool-calling for mortgage calculations and comparable-sale lookups, session memory for rejected
listings that persists across restarts, fair-housing guardrails on every request, and a live
compliance dashboard.

## Prerequisites

- Python 3.13
- API keys for:
  - **Google Generative AI** (Gemini embeddings) — used for the vector store and search
  - **Groq** (LLM) — used for the chat agent; currently configured for `llama-3.3-70b-versatile`
- (Optional) A [LangSmith](https://smith.langchain.com) account, for tracing

## Setup

1. **Clone the repo and enter it**

   ```bash
   git clone <repo-url>
   cd propertyiq_aj
   ```

2. **Create and activate a virtual environment**

   ```bash
   python3.13 -m venv .venv
   source .venv/bin/activate
   ```

3. **Install dependencies**

   ```bash
   pip install -r requirements.txt
   ```

4. **Create a `.env` file at the project root** with:

   ```
   GOOGLE_API_KEY=your_google_api_key
   GROQ_API_KEY=your_groq_api_key
   LANGCHAIN_TRACING_V2=true
   LANGCHAIN_PROJECT=PropertyIQ_AJ
   LANGCHAIN_API_KEY=your_langsmith_api_key   # optional, only needed if tracing is enabled
   ```

5. **Build the vector index** (run once, and again any time `data/listings_corpus.md` or
   `scripts/dimensions_config.py` changes)

   ```bash
   cd scripts
   python ingest.py
   ```

   This reads `data/listings_corpus.md`, extracts and enriches fuzzy dimensions
   (school quality, condition) per listing, and writes the FAISS index to `faiss_index/`.

6. **Run the app**
   ```bash
   python chat_app.py
   ```
   This launches a local Gradio UI (and a temporary public share link) with four tabs: **Chat**,
   **Agent Trace** (full tool-call/result detail per turn), **Debug: Full Analysis** (per-search
   breakdown of every listing's inclusion/exclusion reasoning), and **Dashboard** (session-wide
   guardrail trigger rate, match rate, and a search-filter compliance log).

## Running evaluations

Two complementary eval types are included, both isolated from your real data via a separate
synthetic corpus (`data/eval_corpus.md` → `eval_faiss_index/`, never touching `faiss_index/`):

```bash
cd scripts
python ingest_eval.py        # builds the isolated eval index (run once, or after editing eval_corpus.md)
python run_evals.py          # assertion-based suite - checks retrieval correctness
python eval_groundedness.py  # LLM-as-judge - checks generated responses for fabrication
```

Both save timestamped JSON reports to `evals/reports/`.

## Known, documented limitations

These are intentional, evidenced trade-offs — see `docs/task27_error_analysis.md` for the full
investigation behind each:

- **LLM tool-call argument extraction is not fully deterministic.** Whether a qualitative buyer
  criterion (e.g. "good schools") gets correctly passed to the search tool depends on the LLM's own
  judgment each time. Switching to `llama-3.3-70b-versatile` measurably improved reliability over
  the originally-used `openai/gpt-oss-120b`, but this remains a known, documented limitation, not a
  fully solved problem. A deterministic parameter-extraction layer ahead of the LLM would close this
  gap architecturally, but was scoped out for this project.
- **`enrich_dimension()`'s LLM call is non-deterministic even at `temperature=0`** — re-running
  ingestion on identical source data can produce differently-worded (though same-meaning)
  enrichment text, which can shift borderline NLI outcomes between runs.
- **MCP protocol integration was scoped out.** Tools are bound directly via LangChain's
  `bind_tools()` rather than a standalone MCP server — a deliberate trade-off in favor of depth on
  search correctness.
- `requirements.md` is a **best-effort reconstruction**, not a recovered original — the real
  document was lost before this repo's git history begins. See the notice at the top of that file
  for what's evidenced vs. reconstructed.
